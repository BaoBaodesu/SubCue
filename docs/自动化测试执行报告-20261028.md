## 4. 发现的真实 Bug、复现与修复

### Bug：粗剪工程的「分析输入已改变」守卫对缺少文稿基线的工程永远失效

**现象**：打开一个带分析结果（有片段/决策、`analysisVersion > 0`）但工程状态里没有 `analysisScriptText` 的工程后，修改文稿**不会**把结果判为过期：`analysisStale()` 仍为 `false`，导出按钮仍可用，`xmlExportReason()` 为空 —— 用户会用旧分析结果导出，且看不到任何提示。

**根因**：`analysisStale()` 的实现是 `analysisVersion_ > 0 && scriptText_ != state["analysisScriptText"].toString(scriptText_)`。基线只在**本机跑完分析**时写入（`rough_cut_controller.cpp:927`）；老版本工程或外部写入的工程没有这个键时，`toString(scriptText_)` 的默认值正好等于当前文稿，于是「改了文稿」永远检测不到。

**复现**（已固化为用例）：`SubCueRoughCutControllerTests::decisionHistoryFrameRateAndStaleAnalysisGuards`
1. 用工程写盘 API 造一个 `analysisVersion = 1`、有 1 个 recording 与 1 个 decision、但 `state` 不含 `analysisScriptText` 的 `.subcue-roughcut`；
2. `openProject` → `canExport()` 为真；
3. `setScriptText("第一句。第二句。")` → 断言 `analysisStale()`。

修复前实测输出：

```
FAIL!  : RoughCutControllerTests::decisionHistoryFrameRateAndStaleAnalysisGuards()
        'controller.analysisStale()' returned FALSE. ()
D:\DSH\SubCue\tests\cpp\test_rough_cut_controller.cpp(557) : failure location
```

**修复**：[`src/app/rough_cut_controller.cpp:484-486`](../src/app/rough_cut_controller.cpp#L484-L486)，在 `applyProject` 里按保存的文稿回填缺失的分析基线（只在工程已含分析结果时回填，回填发生在 `markSaved()` 之前，不会把工程标脏）：

```cpp
// 老工程或外部写入的工程可能没有记录分析时的文稿基线；用保存的文稿回填，
// 否则改文稿后“分析输入已改变”永远判不出来，导出会带着旧结果继续放行。
if (!project.recording.isEmpty() && !projectData_.state.contains(QStringLiteral("analysisScriptText")))
    projectData_.state.insert(QStringLiteral("analysisScriptText"), project.scriptText);
```

**修复后验证**：同一用例通过；粗剪控制器 10 个用例全部通过；用例里另有 `saveCurrentProject()` 后 `!modified()` 的断言，证明回填没有引入脏标记。把这段回填去掉，该断言会再次失败（上面那段输出就是证据）。

### 测试隔离问题（非产品缺陷）：SubCue 实例运行中跑 CTest 会让云凭据用例失败

- 复现：先启动 `SubCue.bat`，再跑 `ctest --preset windows-release-cuda` → `cloudSettingsDraftAndDiscovery`、`cloudDeletionWaitsForOwner`、`unifiedAiKeySaveClearAndRollback`、`cloudSwitchConflictAndCapability`、`voiceCloudUpdateRevisionAndCancellation`、`voiceFlashUsageAndUnknownResultsAreProtected`、`omniReviewStartsAtZeroProgress` 共 7 个用例 `cloud.save()` 失败；关闭实例后全绿。
- 原因：这些用例通过 `AppController::cloudSettings()` 走 Windows 凭据域，与运行中的实例争用同一条凭据记录。
- 处理：未改产品代码，已写进 [`docs/自动化测试清单.md`](自动化测试清单.md) §1.1 第 3 条，要求跑全量前先关闭实例。

### 不能自动化（或本轮未自动化）

1. **中文排版与 DPI**：CTest 的 QML 用例全部 `QT_QPA_PLATFORM=offscreen`，只能验证状态与几何；字体、缩放（125/150/175/200%）、原生对话框观感必须人工看（清单 §9 UI-01…UI-07）。
2. **真实模型与真实设备**：12 个 opt-in 用例未执行（真实 ASR、真实本地配音引擎、真实音频设备试听、长文压力、真实云端工程验收）。
3. **粗剪 QML 触发层**：22 个 Action/Shortcut、全部 Dialog、拖放、波形缩放、帧步进、连续试听、单片段试听仍为空白区。
4. **Premiere 实际导入**：只能生成验收文件（`writesPremiereAcceptanceFiles` 需 `SUBCUE_PREMIERE_ACCEPTANCE_DIR`），导入动作需人工按 `docs/roughcut-phase1-premiere-check.md` 走。
5. **打包后安装运行**：`SubCuePackagingTests` 只验证包内布局、导入洁净度与隔离 PATH 启动；真实拷到别的机器运行仍需人工。

## 6. 最终仍然存在的风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 粗剪 AI 复核 / 辅助识别只有服务层与核心算法测试，控制器入口无断言 | 改这两个入口可能悄悄断掉候选筛选、`decisionSource=omni`、成本摘要 | 清单 §12 已列为高优先级；改这块时先用假 HTTP 补控制器用例 |
| 导出 WAV 的控制器入口、取消、4 GiB 上限、WAV 防覆盖源无测试 | 长音频导出失败/卡住或误覆盖无拦网 | 导出器层已有用例；改控制器时补 |
| 字幕导航快捷键（确认并下一条、上/下一条、Shift+I/O、Home/End）仍无断言 | 精修流程回归不可见 | 已在 §12 保留为高优先级 |
| 配音句段菜单（合并/删除/上移/替换表/关联字幕）模型层与 UI 都缺断言 | 文稿编辑出错难发现 | 建议先补 `SubCueVoiceDocumentTests`（纯模型成本最低） |
| `analysisScriptText` 回填只覆盖「打开工程」路径 | 极端情况下仍有 fail-open 可能（工程在内存中被外部改为无基线） | 现在的所有加载路径都会走 `applyProject`；再保守可把基线写进工程 schema 校验 |
| 云端凭据用例与运行中实例互相干扰 | 开发者本机跑测试会看到 7 个假失败 | 已写进清单 §1.1 规则；彻底解法是把凭据域隔离到临时命名空间（未做） |
| 12 个 opt-in 用例长期不跑 | 真实模型/真实设备质量无法用 CTest 保证 | 交付前按 §2.2 手动启用一次并留报告 |
| Offscreen 截图不能代表中文排版 | 排版回归只能靠人工 | 保持清单 §9 的人工清单，交付时附原生截图 |
